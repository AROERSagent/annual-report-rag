## 这个项目解决什么问题

大模型直接问财报，有两个致命问题：**它没见过这份年报**，以及**它会一本正经地编造数字**。

本项目的做法是 RAG（检索增强生成）：先从真实年报里把相关段落**找出来**，再交给大模型**照着答**，并要求它标注出处页码。这样答案可溯源，幻觉也被压住。

```
问：比亚迪 2024 年的营业收入是多少？

答：比亚迪2024年的营业收入为 777,102,455 千元 [比亚迪 第228页]。
                                                        └── 这个页码是真的，程序从年报里找出来交给模型的
```

**知识库**：6 家 A 股上市公司 2024 年年报（贵州茅台 / 宁德时代 / 比亚迪 / 美的集团 / 招商银行 / 伊利股份），共 1300 余页、**4366 个文本块**。

## 核心数据

自建 30 题评测集，对比三种检索配置：

| 指标 | 纯向量检索 | 混合检索 | **混合检索 + 重排** |
|---|---:|---:|---:|
| **Recall@5** | 65.0% | 85.0% | **90.0%** |
| Recall@3 | 60.0% | 75.0% | 85.0% |
| MRR | 0.610 | 0.700 | **0.729** |
| 上下文召回率 | 76.0% | 88.0% | 88.0% |
| **未误拒答率** | 64.0% | 80.0% | **88.0%** |
| 引用有效率 | 100% | 100% | 100% |
| 忠实度 | 100% | 100% | 100% |
| 拒答准确率 | 100% | 100% | 100% |
| 延迟均值 | 1.11s | **1.12s** | 3.77s |

### 三个结论

**① 混合检索是"免费午餐"** — Recall@5 从 65% 提到 85%，而延迟几乎不变（1.11s → 1.12s）。BM25 只是内存里的词频计算，成本可忽略。

**② 重排用 2.65 秒换 5 个百分点** — Recall@5 85% → 90%，但延迟涨到 3.77s（3.4 倍）。所以默认配置用 `hybrid`，对准确率要求更高时才切 `hybrid_rerank`。

**③ 优化检索没有牺牲可靠性** — 三种模式下忠实度、引用有效率、拒答准确率全部保持 100%。

> 详细的评测方法论、指标定义，以及[为什么混合检索在一道题上反而退化](#一个诚实的反例)，见后文。

## 技术栈

| 层次 | 技术 | 为什么选它 |
|---|---|---|
| 文档解析 | **PyMuPDF** | 实测 pypdf 对部分中文年报会抽成乱码，PyMuPDF 能正确解码且快 10 倍 |
| 文本分块 | LangChain `RecursiveCharacterTextSplitter` | 按「段落→句子→字符」优先级递归切分，避免切断语义 |
| 向量模型 | `BAAI/bge-small-zh-v1.5` | 中文专用，512 维，本地运行免费 |
| 向量库 | Chroma | 嵌入式，无需部署数据库服务 |
| 关键词检索 | `rank_bm25` + `jieba` | 补齐向量检索对精确会计术语的短板 |
| 重排模型 | `bge-reranker-base` | 交叉编码器精排，解决 RRF 粗排的盲点 |
| 大模型 | DeepSeek | 兼容 OpenAI 协议，约 1 元/百万 token |
| 后端 | FastAPI + Uvicorn | 自动生成 OpenAPI 文档 |
| 流式输出 | SSE | 首字延迟 **0.20s** |
| 前端 | React 19 + Vite | 对话界面、引用高亮 |

> **关键选型**：向量模型和重排模型都通过 `fastembed`（onnxruntime）加载，**不依赖 torch**。依赖体积从约 500MB 降到 60MB，CPU 上跑得也快 —— 对学生机器很友好。

## 快速开始

### 1. 安装依赖

```bash
git clone https://github.com/你的用户名/annual-report-rag.git
cd annual-report-rag
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

### 2. 配置 API Key

去 [platform.deepseek.com](https://platform.deepseek.com) 注册，创建 API Key，然后：

```bash
copy .env.example .env          # Windows
```

编辑 `.env`，填入你的密钥：

```ini
DEEPSEEK_API_KEY=sk-你的真实密钥
```

> ⚠️ **两个 `.env` 别弄混**：`.env` 是你的真实配置（已被 `.gitignore` 排除，不会提交）；
> `.env.example` 是给别人看的模板，**永远只放空值**。

### 3. 下载数据并建立向量库

```bash
python -m app.ingest --fetch
```

这条命令会依次完成：从巨潮资讯网自动下载年报 → PyMuPDF 抽取 → 分块 → 向量化 → 写入 Chroma。

- 首次运行会自动下载中文向量模型（约 100MB，走 hf-mirror 镜像）
- CPU 上向量化 4366 块约 2 分钟
- 已下载的 PDF 会自动跳过，不会重复请求

### 4. 开始提问

```bash
python main.py
```

会弹出交互菜单：

```
  [1] 命令行问答          ← 推荐先试这个
  [2] 启动 Web 后端       FastAPI，端口 8000
  [3] 启动 Web 前端       React，端口 3000
  [4] 环境自检            检查依赖、模型、相似度
  [5] 重新建立向量库
  [6] 从巨潮下载年报
  [7] 只测检索            排查检索问题用
  [8] 跑评测              30 题，输出 Recall@k 等指标
```

**不用记任何命令**，点菜单即可。

## 评测与消融实验

### 评测集怎么建的

30 题，分三类：

| 类型 | 数量 | 标准答案怎么来的 |
|---|---:|---|
| 可答题 | 20 | 从向量库抽一段原文，让大模型据此出题 —— **答案所在页在构造时就确定，无需人工标注** |
| 数值题 | 5 | 手工编写，考察能否精确定位到含数字的表格 |
| 查不到题 | 5 | 手工编写（如"特斯拉的营收"），考察模型会不会编造 |

**诚实的局限**：自动出题会偏向原文措辞，比真人提问容易。所以评测结果按题型分开统计，不拿容易的题冒充整体水平。

### 五个指标的定义

| 指标 | 怎么算的 |
|---|---|
| **Recall@k / MRR** | 标准答案所在的页，有没有出现在检索结果前 k 名里 |
| **上下文召回率** | 让大模型判断：检索到的资料够不够回答问题 |
| **引用有效率** | 解析回答里所有 `[公司 第X页]`，检查这些页是否真的在检索结果里 |
| **忠实度** | 让大模型当评审：回答的每个结论是否都能在原文找到依据 |
| **拒答准确率** | 对语料里没有的问题，模型是否老实说查不到 |

### 为什么瓶颈在"检索"而不是"生成"

基线跑完时看到一个反常现象：**Recall@1 = Recall@3 = 60%** ——
说明检索结果**要么排第 1，要么前 5 名里根本没有**，没有中间状态。

再看当时答错的 8 道题，**没有一道是编造**，全是老实回答「年报中没有找到相关说明」。
这就把瓶颈精确定位到了检索层：

```
检索不到 → 模型老实说"找不到" → 表现为"误拒答率 36%"
```

所以优化目标非常明确：**把 Recall 提上去，误拒答率会自动下降**。
最终未误拒答率从 64% 提升到 88%，验证了这个判断。

### 指标本身也修过一次

最初用的是「页级命中」：标准答案是出题时那段原文所在的页。
但实测发现它**大量假阴性** —— 比如「招商银行不良贷款率」标在第 44 页，
而检索返回的第 33 页是「3.4.3 按行业划分的贷款及不良贷款分布情况」，
里面明明就有不良贷款率。原因是同一信息在年报里会出现多次（摘要、正文、附注各一遍）。

RAG 真正该问的是「检索到的资料够不够回答问题」，而不是「有没有命中某个特定页」。
所以补了「**上下文召回率**」这个由大模型判定的指标，两个指标一起报告。

### 一个诚实的反例

混合检索**不是在所有题上都更好**。有一道题它反而退化了：

| 问题 | 纯向量 | 混合检索 | 混合+重排 |
|---|---|---|---|
| 「比亚迪的CEO是谁」（答案在比亚迪年报第 57 页） | ✅ 第 4 位 | ❌ 丢出前 5 | ✅ **第 1 位** |

**原因**：`比亚迪` 这个词在向量库里出现在 **795 个文本块**中。BM25 于是返回一大堆
"确实是比亚迪、但页码不对"的块，RRF 把它们排了上去，正好把向量检索本来排第 4 的正确页挤出了前 5。

**这暴露了 RRF 的盲点**：它认为「BM25 排第 1」和「向量排第 1」一样可信，
但无法判断 BM25 那个第 1 其实是靠一个没有区分度的公司名混上来的。

**交叉编码器重排正好解决这个**：它把「问题 + 候选原文」拼在一起真正读一遍，
能识别出"这页在讲财务报表，跟 CEO 没关系"，于是把第 57 页推到第 1 位。

### 剩下 3 道错题的真实原因

| 问题 | 真实原因 |
|---|---|
| 宁德时代政策法规 | **数据抽取缺陷**：第 12 页只有标题「4、主要法律法规及行业政策」，正文没抽出来 |
| 招商银行不良贷款率 | **题目本身有问题**：年报只给分行业/分产品的分类不良贷款率，没有"全行整体"这个数 |
| 宁德时代关联交易 | 检索确实没找到该公司的关联交易段落 |

**没有一道是模型编造** —— 再次印证瓶颈在数据和检索，不在生成。

### 复现方式

```bash
python eval/build_questions.py      # 生成评测集
python eval/run_eval.py             # 跑评测

# 消融实验：切换检索模式各跑一遍
RETRIEVAL_MODE=vector        python eval/run_eval.py
RETRIEVAL_MODE=hybrid        python eval/run_eval.py
RETRIEVAL_MODE=hybrid_rerank python eval/run_eval.py
```

## 踩坑记录

这些都是真实调试出来的，每条都有现象、定位、根因和量化结果。

### 坑 1：PDF 抽取乱码，差点毁掉整个项目

- **现象**：问「招商银行不良贷款率」，返回的第一条居然是**宁德时代**的年报，检索距离 0.79（很差）
- **定位**：先用 `scripts/search.py` 确认检索行为，再**直接全库搜原文** ——
  发现「不良贷款率」在 383 万字里出现 **0 次**。招行年报不可能不提这个词，所以问题在数据层，不在检索算法
- **根因**：该 PDF 使用自定义 CID 字体编码，pypdf 解出的是乱码：
  `ᅱഅၿྛٺܢႵ��ඳ`（应为「招商银行股份有限公司」）。
  pypdf 自己警告过需要 `fontTools`，但装上 fontTools 后**仍然乱码**
- **解决**：横向对比三种解析器 —— pypdf ❌ / **PyMuPDF ✅** / **pdfplumber ✅**，
  最终选 PyMuPDF（C 实现，1300 余页只花 **2.3 秒**抽取）
- **效果**：检索距离 **0.79 → 0.43**，从"检索到错误的公司"变成"精确命中 3.4.3 按行业划分的贷款及不良贷款分布情况"
- **教训**：**RAG 系统的上限由数据质量决定。调检索之前，先验证抽取质量。**

### 坑 2：中文词被空格切碎

- **现象**：同样是「不良贷款率」，有时能命中、有时完全命中不了
- **定位**：统计全库后发现「不良贷款率」共出现 **27 次，其中 13 次**被写成了「不良 贷款率」
- **根因**：PDF 按字形排版，抽取时会在中文词中间插入空白字符
- **解决**：清洗阶段用正则删除中文字符之间的空白
  `(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])`，只处理「中文与中文之间」，不影响英文和数字
- **教训**：这一步是后面 BM25 混合检索能不能用的**前提** —— 字面匹配对"被切碎的词"完全无能为力

### 坑 3：缓存了集合对象，重建后接口全挂

- **现象**：重建向量库后，网页突然打不开了，必须重启后端才恢复
- **根因**：`get_collection()` 加了 `@lru_cache`。重建时集合被删掉再新建，
  但正在运行的后端还攥着那个**已经被删除的旧集合对象**
- **解决**：只缓存 `client`（创建开销大），集合对象每次现取（开销极小）。
  重建后下一次请求自动用上新集合
- **教训**：缓存有状态对象时，要想清楚它的生命周期

### 坑 4：删目录被文件锁挡住

- **现象**：后端开着时重建，Windows 报「文件正由另一进程使用」
- **根因**：早期版本用 `shutil.rmtree` 删整个向量库目录，而 Chroma 的数据文件被占用
- **解决**：改成删 Chroma 里的**集合**（数据库操作，不碰文件系统）。
  顺带还有个好处：以后项目里如果有多个集合也不会误伤
- **教训**：换个抽象层次，问题自然消失 —— 而不是去加 try/except 绕开

### 坑 5：评测指标本身有缺陷

- **现象**：明明检索到了正确答案，却被判为"未命中"
- **根因**：页级命中太严格，同一信息在年报里有多处出处
- **解决**：新增「上下文召回率」，由大模型判定资料够不够回答问题
- **教训**：**指标错了，优化方向就会错**。发现问题先怀疑指标，再怀疑代码

## 已知局限

这个项目不是完美的，以下是明确的可改进点：

| 改进方向 | 说明 |
|---|---|
| 评测集扩到 100 题以上 | 现在 30 题置信区间太宽，1 道题就是 3.3 个百分点 |
| 增量索引 | 现在是全量重建（4366 块约 2 分钟）；可记录 PDF 哈希，只处理新增/修改的文件 |
| 表格单独通道 | 现在表格被当纯文本处理，数字的行列关系丢失 —— 这是年报问答最难的部分 |
| `chunk_size` 参数扫描 | 现在 500 是经验值，应固定评测集扫 256/512/1024 |
| 多轮对话 | 现在是无状态单轮；可用 LLM 做查询改写（"它的毛利率呢" → 补全公司名） |
| 更强的 embedding | bge-small 只有 512 维，换 bge-base / bge-m3 应能提升召回 |

## 常见问题

**Q：`python -m app.ingest` 报 `No module named app`**

你不在项目根目录。先 `cd` 到项目根目录再执行。

**Q：下载向量模型时卡住或超时**

`app/config.py` 已经设置了 `HF_ENDPOINT=https://hf-mirror.com` 镜像。
如果仍然失败，检查网络，或改用 ModelScope 镜像。

**Q：向量化太慢**

正常。年报很长（每份 200+ 页），首次建库需要几分钟。之后提问不再需要重新向量化。

**Q：回答里的页码和印刷页码对不上**
